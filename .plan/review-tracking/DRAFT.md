# 1. What this document is and how it was written
This file is the single build instruction for the CF multi-part product. It replaces the earlier 1024-line draft and the numbered 2048-line draft that the operator rejected for being a checklist instead of an explanation. From here on the document is written in paragraphs, and every section is exactly thirty-two lines: one heading, thirty lines of prose, one blank line. Sixty-four sections make exactly 2048 lines. Nothing in it is invented; where a fact came from an earlier session it is named, and where a fact is missing it is called an unknown.
The operator's complaint was specific and fair. Numbered one-line facts explain what to do but never why, so a reader cannot judge an edge case. Paragraphs force the writer to connect cause and effect, to name the artifact that produced a claim, and to say what happens when a rule is broken. This document therefore uses bold lead-ins for scannability but always continues into full sentences. The structure is uniform on purpose: a reader can jump to any section and still find purpose, rules, and gate.
There are three audiences. The operator reads the context and naming sections to confirm that the product matches what was asked for across many sessions. The implementing engineer reads the part and phase sections to know exactly which files to touch and which command proves the change. The reviewer reads the provenance and gate sections to check that no vendor artifact was mislabelled and no invariant was quietly loosened. Every section serves at least one of those readers, and none is filler.
The document is also a record. The project has already survived several restructures, a translation-damage repair, a naming cycle that renamed the same part three times, and one rename that was blocked by a file handle. Writing those events down is not nostalgia; it is how the next engineer avoids repeating the same failure. When a rule looks arbitrary, the paragraph beside it usually explains which incident produced it. That is the difference between a plan and a set of instructions.
Scope is merged from three options that were previously separate. Option A is the launcher plus the eight-part wiring. Option B is the three reverse-engineering seats: Zingma, Sonar, and Zenix. Option C is the Aster rebrand plus the inbuilt bundle. The operator asked for all three in one document, so the phases run baseline, launcher, wiring, seats, then rebrand and bundle. Each phase ends with the same gate, which is what keeps a merged plan from becoming three plans in a trench coat.
Read the context sections first if you are new. Sections two through nine describe the product and the history of this session. Sections ten through twenty describe the registry, the gates, the aliases, and the provenance model. Sections twenty-one through twenty-three are the Aster rename, which is the immediate next action. Sections twenty-four onward are the build detail, and the last four sections are phases 0 and 1, phases 2 and 3, phase 4, and verification with risks and open questions. If you only have five minutes, read section fifteen and section twenty-two.

## 2. What CF is, in plain terms
CF is a collection of desktop surfaces that share one launcher and one naming registry. Each surface is called a part, and each part owns a folder under `windows/`. The parts are deliberately heterogeneous: one is a monorepo fork, one is a reverse-engineered editor build, one is a browser fork, one holds official vendor packages, one is a CLI workspace, and three are reserved seats for builds that do not exist yet. The product is the arrangement, not any single part.
The project did not start as an eight-part product. It started as a single application at the repository root, with an editor window and an agents window inside it. Over several sessions the operator split the idea into a launcher with no product logic and a set of windows that the launcher starts. That decision is why the repository now has a `launcher/` folder and an `arch/` folder instead of a single `src/`. The parts are the consequence of that split, not a separate invention.
Every part is addressed by a codename that is also its folder slug in lowercase. Ingot, Aster, Chromix, Codeix, GSX-CLI, Zingma, Sonar, and Zenix are the eight codenames. Aliases are edition labels layered on top: Lite, Plus, Pro, Studio, Max, and Ultra. A codename is identity and never changes casually, while an alias is a label that can be reassigned. Confusing the two is the most common source of naming drift in this repository.
The registry at `arch/windows.json` is the single source of truth for names, folders, aliases, contents, and status. `arch/brand.ts` mirrors it for TypeScript, and every `window.json` is generated from it by a script. The launcher reads the registry rather than hardcoding a list. That architecture is why the Onyx-to-Aster rename is a data edit plus a folder move plus a regeneration, and not a hunt through a hundred files. It is also why the rename still needs a checklist: a registry edit without the folder move leaves a dangling path.
The product deliberately has no roles. Ingot is not the main part even though it is the largest tree on disk. No card is styled as primary, no script starts a part implicitly, and no document calls any part the flagship. This was decided explicitly after an earlier draft implied that the monorepo was the centre. The rule exists so that the empty seats are not treated as secondary, and so that a future decision about roles has to be made out loud rather than assumed.
Finally, provenance is part of the product statement. A reader must be able to tell which surface is a fork, which is a reverse-engineered build, which is an official package used as-is, and which is native. A part that hides its provenance invites assumptions about support, updates, and licensing that are not true. Sections fourteen through twenty define the labels, and every part's registry contents line carries its label in plain words.

## 3. Session history, part one: baseline repair and CJK damage
The earliest work in this thread was repairing a repository that had been damaged by a translation pass. A large set of strings had been converted to CJK characters and back, leaving escaped quotes, broken JSON, and TypeScript files with mangled string literals. The build failed with an invalid built-in provider configuration, and the failure was not a single bad value but dozens of files with the same class of damage. Repairing one file at a time would have taken days, so the work moved to parser-driven scripts.
Two repair scripts were written. One repaired escaped quotes in JSON by re-escaping known patterns, and it fixed sixty-three strings across the built-in provider configuration and its test fixture. The other repaired TypeScript string quoting by parsing the file and rewriting the damaged literals, and it touched more than a dozen files including the artifacts module, the world-run module, the hole-sites module, and the engine tests. A generated library file was deleted and regenerated rather than patched, because its forty-four megabytes were entirely double-escaped.
The repair was verified two ways. First, the JSON files parsed and the provider configuration loaded. Second, the root typecheck ran to completion with an eight-gigabyte heap and reported zero errors. The heap flag matters: without it the typecheck exits with an out-of-memory code, which looks like a compiler bug and wastes time. That flag is now part of the documented baseline, and the phase-zero section repeats it so nobody rediscovers it the hard way.
The CJK incident produced two lasting rules. Generated files are regenerated, never patched, because a patch cannot reliably undo a systematic transformation. And every JSON and TypeScript file in the tree must parse before a phase is declared green, because a single unparsed file can hide behind a successful build of an unrelated package. Both rules live in the constraints sections, and both are checked during the baseline phase.
A secondary repair was needed for the internationalisation package, whose Simplified Chinese locale file had been deleted during the purge. It was recreated as a thin fallback to the English locale so that the build could resolve the module again. That is a stopgap, not a translation; the section exists here so a future reader does not mistake the fallback for real localisation work. Real translation is out of scope for this plan and would require a separate decision.
The lesson carried into later sessions is that damage is usually systematic, not random. When several files fail the same way, the right response is a script and a verification pass, not manual editing. When one file fails differently, the right response is to read it. The project has already paid for this lesson twice, once with JSON and once with a generated TypeScript library, and the constraints sections encode it so it is not paid again.

## 4. Session history, part two: Repo Wiki and the Qoder evidence
The main feature request that started this thread was a Repo Wiki: a per-repository knowledge surface with an index, per-module documents, and a store. The original implementation plan assumed a design from scratch, but the operator corrected that assumption sharply. The request was to recover the real behaviour from shipped Qoder artifacts, not to invent a lookalike. That correction changed the whole approach from design to evidence collection.
The evidence came from the installed application's shared cache and from the unpacked Electron resources. The feature flag file contains `repoWikiEnable`, and the ignore file name is `.qoderignore`. The agents window bundle registers sixteen `wiki/*` IPC methods, including create, read, update, and status calls. The local knowledge database has three tables: `agent_knowledge_task`, `agent_knowledge_upload`, and `agent_knowledge_workspace`. Those names are observations read from the artifacts, not inferences.
The on-disk layout was recovered the same way. Snapshots live under `wiki_snapshots/<hash>/<lang>/` with `metadata.json`, `mtree.json`, and a `files/` tree. The workspace key has the shape `<project>#wiki#<branch>#wiki#<lang>`, with sentinel values `Q0DeR-MaG1C-BrAnCh-Fo2-NoN-GiT-Or-No-C0MmIt` when the repository has no branch or no commit. The module tree has caps: two hundred fifty thousand enumerated files, one hundred thousand indexed files, a directory depth of one hundred, and ten thousand files per directory.
Those numbers were not decorative. They were implemented in the scanner so that a large repository cannot exhaust memory or time. The scanner reads the ignore file, applies a glob matcher, enforces the depth and per-directory caps, and produces a workspace key using the same sentinel logic. Tests cover the ignore behaviour, the caps, and the shape of the generated key. The service writes snapshots in the recovered layout so that a reader familiar with the vendor's cache can navigate ours without a map.
The feature was then aligned with the existing product: the export path is `.cf/repowiki`, the ignore file constant is exposed so callers do not hardcode it, and the workspace-key helper lives in the shared package. Eight tests pass across the scanner and the service. The point of recording all of this here is not to re-litigate the design; it is to show that the feature's rules came from artifacts, and that the same evidence-first method is what the provenance sections now require of every part.
One caution belongs in the record. An early demonstration fabricated a wiki with invented content, and it was deleted once the operator noticed. That mistake is the reason the provenance and evidence sections are strict about observations versus inferences. A plausible-looking artifact is not evidence, and a generated document that was never produced by the real pipeline is worse than no document, because it teaches the wrong behaviour.

## 5. Session history, part three: MAD restored natively
The operator asked for MAD to be restored natively, the way an older tree had it. The old tree carried a runtime, a package, and a skill, and the two were wired together through the command surface. Restoring it meant three things at once: a control plane that actually schedules and arbitrates, a command that an operator can call, and a skill that tells the assistant when to use it. Anything less would have been a stub with a familiar name.
The control plane was rewritten as a real runtime. It has a router with empirical history so repeated failures steer away from a bad strategy, a scheduler with budgets and backoff, a discussion bus that converges proposals, evidence-gated claims so a claim without support cannot win, an arbiter that stays undecided on ties, and snapshot and restore so a run can be inspected and resumed. The runtime writes run files under `.cf/mad/runs/` and keeps an orders file beside them. Those paths are the contract the command and the skill both rely on.
The command surface exposes the operations an operator actually needs: status, run, list, show, discuss, claim, resolve, arbiter, complete, cancel, and finalise. It was wired into the main command tree so it behaves like any other subcommand, including help output. A bug where identical claim text produced duplicate identifiers was fixed by deriving the identifier from a hash of the text plus a counter. That detail is recorded because duplicate identifiers make an evidence ledger unusable, and the fix is not obvious from the symptom.
Thirteen tests were written and all pass: seven for the runtime and six for the command. The runtime tests cover routing history, scheduling backoff, evidence gating, arbitration on ties, and snapshot restore. The command tests cover the operations and the duplicate-claim case. A skill document was written so the assistant knows the workflow and hands off to the workflow system at the right moment, rather than improvising a schedule.
Two integration obstacles were solved during this work. The command initially imported a context type from the wrong package, which produced a module-not-found error in the editor; the fix was to import from the Cordis package that the runtime actually uses. And the command depended on a formatting helper from the core package that was not resolvable in that build order, so a local formatter was used instead. Both fixes favour fewer cross-package edges, which matters in a tree that has already been restructured twice.
The MAD work is the reason the phase sections insist on evidence blocks. The runtime's whole design is that a claim needs support, so a plan that says a phase is done without pasting the command output would contradict the feature it is documenting. That is not a stylistic preference; it is consistency between the product and the process that builds it.

## 6. Session history, part four: skills vendored and rebranded
The operator asked for every slash skill that the reference environment had and this repository lacked, with duplicates skipped and no product naming left behind. The work began with an inventory: which skills exist, which are already present, and which are platform specific. The inventory mattered because copying a skill twice creates two sources of truth, and deleting a platform adapter because its name looks vendorish breaks the harness that runs the skill.
Forty-seven skills were copied, along with four bundler plugins. One command-defined workflow was materialised from its payload so it exists as a file rather than as a menu entry. A provenance document was written that records the source root, the file count, the main file, and a hash prefix for each vendored directory. That document is the only authority on which files may be rebranded; everything else in the vendored set is left alone even if it mentions the vendor.
Two hundred thirty-nine tokens were rebranded by a script. The rule was narrow: product-name tokens in prose, and path prefixes that pointed at the vendor's configuration directory. Datasets, fixtures, and platform adapters were excluded. Excluding datasets is not squeamishness; a dataset that describes a vendor's product must keep describing it, or the skill's examples become false. Excluding adapters is practical: their file names are part of the runtime contract.
The vendored set now lives under `inbuilt/bundle/skills`, with a verified count of four hundred forty-six files and three point three four megabytes. It includes product skills such as the Repo Wiki generator and the MAD workflow, plus the vendored harness set. The folder is not referenced by any part yet, which is why the plan has a wiring section rather than a claim that everything already works. A copied skill that no part loads is inventory, not integration.
A rule emerged that is now enforced in the documentation phase: no skill may claim official support for a vendor feature, and no skill may describe a reverse-engineered build as supported software. Skills that touch RE work must carry the label. The operator has been consistent about this for the whole session, and a skill that quietly drops the label would undo that consistency faster than any code change.
The last part of the skills story is the rebrand script itself. It is kept in the tree, it is idempotent, and it logs every file and token count it changes. When a future vendoring pass happens, the script runs again and the provenance file is regenerated. Manual edits to vendored skills are treated as drift, because the next vendoring pass would silently overwrite them.

## 7. Session history, part five: the desktop binary, extracted and proven
The operator rejected a web-server-based imitation and demanded a real desktop application built from the shipped binary. The response was to copy an installed Qoder build, verify that the native executable's hash was identical to the original, extract the resource layer, and produce a modifiable tree. The copy contained four thousand seven hundred three files at eight hundred forty-two megabytes, and the native executable hash began with `43c31ca5` and ended with `dd4441`, matching the source exactly.
The extraction produced two layers. The native layer is one hundred fifty-three files at roughly five hundred forty-six megabytes. The source layer is three thousand seven hundred seventy-eight files at roughly two hundred eighty megabytes, and its manifest has four thousand seven hundred three rows. The main process bundle is sixty thousand two hundred sixty-five lines after beautification, the CLI is nine thousand two hundred three, the agents window is one million nine hundred seventy-nine thousand five hundred ninety-one, and the workbench is a similar magnitude. Those counts are the proof that the source layer is real rather than a stub.
Identity edits were deliberately minimal. The product configuration and package manifest were renamed, the local service binary was renamed to match the new executable name, and one window-title literal was patched in the main bundle. Everything else was left alone. The launch was verified by starting the copy and observing twelve processes with both top-level windows titled as configured, plus screenshots stored with the evidence. No crash dialog appeared.
The hard limit was documented at the time and must survive into this plan: there is no C plus plus or Chromium source for the host, so the JavaScript resource layer is the only modifiable surface. Any plan that assumes deeper changes is wrong, and any promise about rebuilding the host is a promise nobody can keep. The RE label follows from this: the build is a renamed and lightly patched vendor application, not a reimplementation.
The evidence layout from this work is the model for every other part. A README explains what was extracted and how, a manifest lists every shipped file with a hash, a beautified directory holds readable copies, and screenshots sit beside the claims they support. Offsets and versions are recorded together so a vendor update can be recognised as invalidating the notes. That layout is repeated in the evidence section of this plan rather than described again from scratch.
This part is now being renamed from Onyx to Aster. The rename is mechanical: the folder moves, the registry codename changes, the alias stays Studio, and every generated file is rewritten. What does not change is the evidence, the executable name, or the extraction. Section twenty-two lists the exact files, because a rename that misses one generated manifest is exactly the kind of drift the gate was built to catch.

## 8. Session history, part six: the naming cycle
Naming consumed more of this session than any code change, and the record is worth keeping because the operator corrected several invented names. The first set was Titanium, Obsidian, Prism, and Aether. Then Aether became Zingma under a rule the operator stated explicitly: take Lingma and replace the leading L with Z. Then Titanium was renamed to Maxxi, and later to Ingot. Then Obsidian became Onyx, and now Aster. Prism was briefly replaced by Magnus, and Magnus was dropped entirely.
Two names were invented by the assistant and rejected, which is the reason the current rules say a codename must come from a decision and not from a suggestion. The operator also corrected a factual error: Codeix is the OpenAI Codex surface, not a Claude surface, and Zenix is the native Claude Desktop seat. An earlier draft had those two swapped, and the correction is recorded here so the mistake is not reintroduced by a future summary that lost the detail.
The alias ladder also changed twice. It began as Core, Lite, Pro, Studio, Max, Ultra. Core was retired, and Plus was inserted between Lite and Pro at the operator's request, which produced Lite, Plus, Pro, Studio, Max, Ultra. The retired label renders as `#`, and two parts, Chromix and GSX-CLI, hold no alias at all. The distinction between retired and absent is documented because the UI renders both the same way while the registry treats them differently.
The launcher's own name was settled late. An earlier proposal used a product-name prefix, and the operator rejected any part being named CodeFusion. The final decision is that the product is called Launcher Desktop and its window title is exactly Launcher. The only surviving CodeFusion string is the executable file name in the Aster folder, and renaming that is a separate mechanical step with its own gate because it touches identity fields and profile paths.
Several names were suggested and not chosen, and they are recorded as dropped rather than forgotten: Maxxi, Titanium, Aether, Prism, Magnus, and the phrase CodeFusion Max. A future reader who sees one of those words in an old document should treat it as history. The naming section of the registry notes field records the current state in one sentence so that raw JSON is self-explanatory without opening this document.
The practical lesson is that renaming a codename is expensive and renaming an alias is cheap. Codename changes move folders, break handles, invalidate documentation paths, and require regeneration. Alias changes touch four fields. Every naming decision from here should ask whether the label is enough, because the cheap change is almost always the right one when the surface has not changed character.

## 9. Session history, part seven: restructure, gate, and the inbuilt bundle
The repository was restructured into a flat, purpose-named layout. The root now holds `arch/`, `launcher/`, `windows/`, `inbuilt/`, `scripts/`, and `BRAND.md`, with the old tree parked read-only under `.dead/` behind a notice file. The monorepo moved into `windows/ingot`, the reverse-engineered build into `windows/onyx` and now `windows/aster`, and the browser and CLI forks into their own folders. The restructure is why every script derives its root from its own location instead of assuming a working directory.
A consistency gate was written during the restructure because prose kept going stale. The gate compares the registry against the launcher HTML and the launcher manifest, checks that card count and order match the parts array, checks that ladder keys equal resolve keys, checks that every assigned alias is on the ladder, checks that every part folder exists, and checks that every alias points at a real codename. It prints eight PASS lines and a summary, and it exits non-zero on any drift. Today it reports eight of eight.
A migration script followed the folder rename from `architecture` to `arch` and updated every reference, including the report. That rename is a small example of the larger problem: a path appears in the registry, in the mirror, in the launcher script, in the launcher readme, in the architecture readme, in the brand document, in the report, and in several one-off scripts. Missing one is not a typo, it is a broken command for the next person. The gate catches some of those, and the documentation phase catches the rest.
The `inbuilt/` tree was added to hold payloads that belong to the launcher rather than to a part. It currently holds four hundred forty-six skill files at three point three four megabytes, three unidentified extras at two point six four megabytes, and three empty reserved seats for agents, bundled assets, and plugins. Each seat is documented as empty rather than hidden, because an empty folder with no note looks like an accident and invites deletion.
One restructure incident is worth remembering. The folder rename from Obsidian to Onyx was blocked by a file handle, so a junction was used temporarily and documented as a workaround. The junction was later replaced by a real folder when the handle cleared. The lesson is not that junctions are bad; it is that a workaround must be documented in the same place as the final state, or a later reader will treat the workaround as the design. The current Aster rename repeats this risk and is planned with a handle check first.
The restructure also produced the report's current-state section, which supersedes earlier path references without rewriting history. That pattern, supersede rather than erase, is used throughout this plan. Old sections stay for audit, a new section states the truth, and the gate checks the truth where it can. The next rename will add another superseding section rather than editing the old one into silence.

## 10. Current state of the tree
The repository root contains `arch/`, `launcher/`, `windows/`, `inbuilt/`, `scripts/`, and `BRAND.md`, plus the dot-directories for git, hooks, editor settings, local agent state, the parked tree, and the external harness skills. There is no root package manifest and no root build pipeline for the launcher; the launcher is dependency free by design, and the monorepo with its package manager lives inside Ingot. That separation is the reason the launcher can be inspected and started without installing anything.
`arch/` holds three files: the registry, the typed mirror, and the readme that documents the tree and the procedures. It is the smallest directory and the most important one, because a change here propagates to every generated file. Nothing in `arch/` is generated, and nothing outside `arch/` is allowed to be the authority on naming. When a rename happens, the registry changes first and everything else follows in the same commit.
`launcher/` holds the static shell, the PowerShell entry point, the generated identity manifest, and a readme that lists the seats and the startable entries. The shell is plain HTML with inline styles and no external fetches, and the script is the only executable entry point a human uses today. The manifest exists so a future packaged host can read identity without parsing HTML, and it is rewritten by the sync script rather than edited.
`windows/` holds the eight part folders. Ingot holds the monorepo. Aster holds the reverse-engineered editor build plus its evidence directory. Chromix holds the browser source. Codeix holds two official packages and a toggle. GSX-CLI holds the CLI workspace and the additional source drop. Zingma, Sonar, and Zenix hold only a generated manifest each, because their builds have not landed. Every folder is self-contained and no part reads another part's internals.
`inbuilt/` holds the bundled skills and extras, and `scripts/` holds two tool families: the rebrand and migration tools that keep the tree consistent, and the reverse-engineering tools that produced the Qoder evidence. The tools are ASCII only, idempotent, and derive their root from their own location. Historical rename scripts are kept because they document how the current names were reached, and deleting them would erase the audit trail that this repository treats as part of its value.
The parked tree under `.dead/` is a complete copy of the pre-restructure repository with a notice explaining that it is read-only reference material. It is never launched and never edited. The external skill set under `.agents/` belongs to the assistant environment, not to the product, and it is never shipped or rebranded. Confusing either of those with product content is the fastest way to produce a change that looks correct and breaks something later.

## 11. The registry schema
The registry has five top-level keys: the update date, the naming block, the launcher block, the parts array, and the alias resolve map. The naming block holds the ordered ladder, the retired aliases, and a one-line note recording the current decision in plain language. The launcher block holds the product name, the window title, the folder, the role sentence, the status, and the entry file. The parts array is ordered, and that order is the display order everywhere.
Each part record has five fields: codename, alias, folder, contents, and status. The codename doubles as the display name and the lookup key. The alias is either a ladder value or null. The folder is a repository-relative path. The contents field answers three questions in one sentence: what the folder is, whose artifact it came from, and how large it is. The status is either present or empty, and no other value is allowed.
The alias resolve map is the only place an alias becomes a codename. It must have exactly the ladder's keys in the ladder's order, and every value must exist in the parts array. The PowerShell script reads this map, the typed mirror declares the same mapping, and the gate compares them. A second private map anywhere in the codebase would be a second source of truth, and the first rename after that would produce a silent mismatch.
A provenance field is proposed but not yet added. The shape is an origin object with a kind, a source, and an evidence path. The kind is one of the five labels defined in section fourteen. The source names the artifact or upstream project, and the evidence path must exist on disk. Once added, the launcher can render a provenance badge from data instead of hardcoded prose, and the gate can check that every part declares where it came from.
The contents string is treated as data, not prose. It uses verified numbers, and it carries the provenance label in plain words, for example that a folder holds a reverse-engineered build with an evidence directory, or that it holds official packages and a toggle. Vague phrases such as various files or mostly working are rejected, because the launcher displays this string verbatim and a vague string teaches the reader nothing about what they are starting.
Every field is deliberate, and adding one is a schema decision recorded in this section before it is implemented. The reason is practical: the launcher, the generator, the mirror, and the gate all read the same shape. A field added in a hurry without updating those four readers produces a manifest that parses but means something different, which is worse than a parse error because it fails silently.

## 12. Invariants and the consistency gate
The gate exists because prose drifts faster than data. It currently runs eight checks, each of which encodes an invariant that a rename or a restructure has broken at least once. The checks are not aspirational; each one corresponds to a concrete failure in this repository's history. When a new invariant is discovered, a new check is added, and existing checks are never loosened to make a change pass.
The first four checks cover identity and order. The launcher title must be Launcher in both the registry and the HTML. The launcher manifest must match the registry identity. The card count must equal the part count. The card codenames must equal the part codenames in the same order. Order is checked deliberately, because the parts array is display order and a set comparison would let a reordering pass unnoticed.
The next four checks cover aliases and paths. The resolve keys must equal the ladder keys. Every assigned alias must appear on the ladder. Every part folder must exist. Every alias value must point at a real codename. These four catch the most common rename residue: an alias left pointing at a codename that no longer exists, or a folder path updated in the registry but not on disk.
The gate prints one PASS or FAIL line per check with a detail string, then a summary line with the passed count. It exits zero only when all eight pass. It never writes files, so it is safe to run at any time. Its output is pasted into the phase report verbatim, because a summary that says the gate passed is not evidence; the eight lines are evidence.
Future checks are already listed so they are not forgotten. A skills bundle parity check would compare the provenance list against the skills directory. A manifest byte-equality check would regenerate into memory and compare. A vendor-naming check would scan prose for the product name outside allowed contexts. An ASCII check would fail any script containing non-ASCII characters. An origin completeness check would verify the proposed provenance field.
The gate is the contract between the human procedures and the machine state. A procedure that can be skipped while the gate stays green is an incomplete gate, not an optional step. This is why the rename section names every file and then ends with the gate: the file list is the human half, and the eight checks are the machine half. Both must pass before a rename is called done.

## 13. The alias ladder and resolution
The ladder runs Lite, Plus, Pro, Studio, Max, Ultra, from the lightest surface to the heaviest. Lite belongs to Zingma and is reserved for Qoder's native Quest window. Plus belongs to Sonar and is reserved for the reverse-engineered DeepSeek Harness. Pro belongs to Codeix, the OpenAI Codex surface. Studio belongs to Aster, the reverse-engineered editor build. Max belongs to Ingot, the largest tree on disk. Ultra belongs to Zenix, the native Claude Desktop seat.
Core is retired and maps to nothing. Chromix and GSX-CLI hold no alias at all. The UI renders both cases as a hash sign, but the registry distinguishes them: a retired label once meant something and is kept for history, while an absent label was never assigned. That distinction matters when a new alias is proposed, because a retired label needs a revival decision while a free slot does not.
Resolution tries an exact codename first, case-insensitively with surrounding whitespace trimmed, then an alias. This ordering means an input that is both a codename and an alias resolves to the codename, which is the safer failure mode because a codename is identity and an alias is a label that can be reassigned. The resolver returns a record or nothing, and every caller must handle nothing explicitly.
An unknown input prints the list of known codenames and exits with a non-zero code. It never falls through to a default part, never starts anything, and never prints a stack trace as its main message. The message names what was received and what is accepted, so an operator can correct the command without reading source. This behaviour is tested in the baseline phase.
Aliases never become identifiers. They are not folder names, not window titles, not file names, and not registry keys. That rule is what makes an alias change a four-field edit instead of a rename. The codename changes in this project have all been expensive, with folder moves and handle locks, while the alias changes have been pure data edits. The lesson is embedded in the procedures.
The ladder is product language, so changes to it are product decisions. A new alias is recorded in the brand document with a factual reason, then reflected in the ladder, the resolve map, the part record, and the card. A reason that states a preference instead of a fact is rejected, because the reason is read by future operators who did not participate in the decision and cannot evaluate a preference without context.

## 14. Provenance: labels, policy, and why they are data
Provenance answers the question the operator has asked repeatedly: which part is whose, and which one is reverse engineered. A prose answer in a readme goes stale the moment a part changes character, so provenance is recorded as a label per part with the source artifact and an evidence path. The five labels are RE, FORK, PKG, NATIVE, and UNKNOWN, and every part has exactly one.
RE means the bytes came from a shipped vendor artifact that was extracted and, in some cases, renamed or patched. Aster is RE of the Qoder desktop build. Zingma is RE of the agents window inside that same artifact. Sonar is planned RE of the DeepSeek Harness. RE parts are never described as official, never auto-update, and never redistribute the vendor payload.
FORK means a source tree with upstream lineage. Ingot is a fork in the ZCode lineage. Chromix is a Zephium browser fork. GSX-CLI is an opencode fork with an additional MiMoCode source drop. Forks are modified freely subject to their licences, and their provenance claim is about lineage rather than extraction. The evidence for a fork is the tree itself, plus the manifest names that prove lineage.
PKG means an official vendor package inventoried but not modified. Codeix holds two OpenAI Codex packages under this label. NATIVE means an official application used as-is on this host, and Zenix is the Claude Desktop seat. Both labels carry a strong default: no rebranding, no mutating extraction, no redistribution. A request to rebrand a native app is a decision recorded in the brand document before any file is touched.
UNKNOWN means the artifact has not been identified. Sonar begins here until the host is searched and a candidate is classified. UNKNOWN is temporary by definition and is never a euphemism for not looking; the search itself is a recorded task with commands and output. If nothing is found, the seat ends blocked with that statement rather than with a guess.
The label decides which rules apply. RE parts need evidence files, reversible literal patches, and offline gates. FORK parts need toolchain inventories and build logs. PKG parts need identity and hashes but no extraction. NATIVE parts need payload copies, profile isolation, and licence caution. When a part changes label, for example a package that is later extracted and patched, the label changes in the same commit and the reason is recorded. This is what keeps the provenance table honest over time.

## 20. Evidence layout and the provenance table upkeep
Each part owns an evidence directory unless it already has a stronger location, as Aster does with its source directory. The evidence readme states what was inspected, with what tool, on what date, and what the result was. It lists artifact hashes, extraction directories, and any stubs or patches. It is written for a reader who wants to replay the work, not for a reader who wants a summary that hides the method.
The manifest format is JSON Lines with one record per file containing path, size, and hash. The format is chosen because it diffs cleanly and streams without loading everything into memory, which matters for artifacts with thousands of files. A manifest is regenerated rather than patched, and a mismatch between manifest and disk is treated as evidence drift. Aster's manifest is the model for the other parts.
Screenshots are supplementary and named by milestone, for example first run or post-rebrand. Logs are text, captured with the command that produced them, and truncated to the useful window where they are long. A screenshot alone never proves a technical claim; it proves a visual state, which is sometimes exactly the claim under test, for example that no vendor branding appears on first run.
The report carries a table with one row per part: codename, alias, label, source artifact or project, evidence path, and status. That table is the single place a reader can answer the provenance question without reading eight sections. It is updated in the same commit as any label or evidence change, and the documentation phase checks that every row's path exists before the table is considered done.
The proposed registry field makes this machine-readable. Each record gains an origin object with kind, source, and evidence. The gate then checks that every part has an origin, that the kind is one of the five labels, and that the evidence path exists. Once that lands, the launcher can render a provenance badge from data, and the report table can be generated rather than hand-maintained.
The gate for this section is explicit. Every part must have exactly one label, every label must have a one-line justification, every RE part must have an evidence directory with a readme, every fork must name its upstream and the files that prove it, every package and native part must have hashes without modifications, and the unknown seat must have a recorded search with its output. The table is copied into the phase report with the gate output beneath it.

## 21. The Aster rename: scope, order, and why now
The operator decided that Onyx becomes Aster. The codename changes, the folder changes, and every generated file follows. The alias stays Studio, the executable stays CodeFusion.exe, and the evidence does not move out of the part folder. This rename is happening now because the plan is being rewritten anyway, and a naming change that lands after the plan would invalidate half of its references on the same day.
The order of operations is fixed, because a partial rename is worse than no rename. First, confirm no process holds a handle on the folder, including the editor, the file indexer, and any running copy of the application. Second, rename the folder from windows/onyx to windows/aster. Third, edit the registry codename, folder, and contents. Fourth, update the typed mirror, the launcher card, the launcher script path, and the documentation. Fifth, regenerate every manifest. Sixth, run the gate and paste the output.
The folder rename comes before the data edit on purpose. If the data changes first, the gate fails with a missing folder, which is a correct failure but a confusing one. If the folder changes first, the gate also fails, but the failure points at the registry entry that still says onyx. Either way the gate fails once; the important thing is that the failure is expected and that nobody panics and starts editing generated files by hand.
A handle lock is the realistic failure mode. It happened with the previous rename from Obsidian to Onyx, and it was solved with a junction that was later replaced by a real folder. This time the check is explicit: list the processes, close the editor if it has the folder open, and confirm the rename in one attempt. If the rename is blocked, the work stops, the blocker is recorded with the exact error, and no junction is created as a silent workaround.
The rename also touches history. The report references Onyx in its desktop-binary section, and the brand document references Onyx in the rule about the executable name. Those references become Aster, with a single parenthetical note that the former name was Onyx, so a reader with an older checkout can still find the artifact. Historical sections that describe a past decision keep the name that was current at the time only if changing it would make the record false.
The reason this rename is cheap compared with earlier ones is that the registry exists. The codename appears in a handful of authored files and in generated manifests that are rewritten from the registry. The expensive part is the folder move and the documentation sweep, not the naming itself. That is the proof that the architecture is working: a rename is now a mechanical procedure with a checklist, not an archaeology project.

## 23. The Aster rename: risks, gates, and rollback
The first risk is a handle lock. The editor, the indexer, or a running copy can hold the folder, and the rename fails with a sharing violation. The mitigation is to check processes first, close what can be closed, and attempt the rename once. If it fails, the blocker is recorded and the rename is rescheduled; a junction is not created as a silent substitute.
The second risk is a stale reference in a script. The launcher script points at an executable under the old folder, and a missed edit produces a start failure that looks like a missing build. The gate does not read the script's case labels, so the mitigation is a manual search for the old folder string across authored files, followed by a smoke test of the start entry.
The third risk is generated-file drift. A manifest that still says Onyx means the sync script was not run after the registry edit, or it was run before the folder moved. The mitigation is order: registry edit, folder move, sync, gate. Running sync twice is harmless because the script is idempotent, and running it before the folder exists produces a clear warning rather than a silent skip.
The fourth risk is documentation half-truth. A document that says Aster in the table but Onyx in the prose reads as careless and, worse, makes a search for either name return both. The mitigation is a full sweep with a case-insensitive search for the old codename across authored documents, followed by a decision for each hit: update, or mark as history with the former name in parentheses.
The gate after the rename must show eight of eight. Specifically, the launcher title check, the manifest identity check, the card count check, the card order check, the ladder and resolve check, the alias-on-ladder check, the folder existence check, and the alias-target check. If any of them fails, the rename is not finished, regardless of how many files were edited.
Rollback is simple and must stay simple. Rename the folder back, revert the registry and the mirror, run sync, run the gate. Because the alias and the evidence were never touched, rollback does not lose work. That property is the reason the plan insists on doing the rename as one atomic commit rather than as a series of opportunistic edits spread across days.

## 24. Launcher Desktop: identity and contract
The product is called Launcher Desktop, and its window title is exactly Launcher. It lives in launcher/ with a static shell, a PowerShell entry point, a generated manifest, and a readme. Each card shows the codename, the alias or a hash sign, the folder, the verified contents sentence, and a status pill. The cards follow the registry order, which is also the manifest order. Those three rules are why the shell survives renames: it reads data instead of assuming it, and it says what is true even when the truth is that a seat is empty.

## 27. launch.ps1: modes, input, and resolution
The script takes one optional argument. With no argument it lists the parts. With an argument it resolves the input and either starts the part or reports why it cannot. The list mode prints codename, alias, folder, status, and contents, then the ladder line and the retired labels, and exits zero. The start mode resolves a codename or an alias, prints the resolved codename, and then acts.
Resolution tries an exact codename first and an alias second, case-insensitively, with surrounding whitespace trimmed. The alias map is read from the registry rather than duplicated in the script, so a rename or a reassignment is a data change. An unknown input prints the accepted codenames and exits non-zero, and it never falls through to a default part or starts anything by accident.
The script derives its root from its own location, never from the current directory. That single rule is why the launcher works when invoked from anywhere, including a shortcut, and why the previous folder renames did not silently break it. The registry is read as UTF-8 JSON and parsed with the built-in converter, and a parse failure prints a clear message naming the file rather than a stack trace.
Output is plain ASCII, has no colour codes, no emojis, and no timestamps, so it can be redirected to a file and pasted into a report. Tables use padded columns and stay under a sensible width so they do not wrap in a normal console. Failure messages name the input received, the path searched, and the accepted values, because those three facts are what an operator needs to self-correct.
The script never writes to the registry, never deletes files, never installs anything, and never contacts the network. It is safe to run repeatedly, and running it twice produces the same output rather than a second copy of a process. Those constraints are what allow the gate and the phases to call it without worrying about side effects.
The behavioural tests are manual and few. List mode, an alias input, a codename input, and an unknown input are each run once and recorded. When a start entry exists, it is tested and the process is stopped before the phase ends. That is enough coverage for a script whose surface is deliberately small, and it avoids building a test harness for four behaviours.

## 28. launch.ps1: start entries and process hygiene
Two parts have start entries today. Ingot starts the package manager's desktop development command inside its folder. Aster starts the executable inside its folder. Every other part prints its contents and folder and starts nothing, which is the honest behaviour for a seat or for a fork whose toolchain is not installed. Adding an entry requires a proven run first, not a guess that a command should work.
The Ingot entry fails cleanly when the package manifest is missing, and it records the package manager version in its output so the evidence shows what actually ran. The Aster entry fails cleanly when the executable is missing, and it uses the process launcher rather than a direct invocation because the application needs to detach from the terminal. No other part uses the process launcher.
Process hygiene is part of the contract. Any process started during a phase is stopped before the phase ends, and the evidence records the process state before and after. A development server may be observed for a short window to confirm that a window appears, and then it is terminated. Leaving a server running holds folder handles, and folder handles are exactly what blocked the previous rename.
The script never starts two parts in one call and never starts the same part twice. If a part is already running, the script does not attempt to detect it and manage it; it starts a new process only when asked, and the operator is responsible for not asking twice. That is a deliberate limit: process management is out of scope for a launcher that is meant to be dependency free.
Start entries live in one switch statement, and each entry names the folder it expects. When a part is renamed, the entry moves with it in the same commit as the registry change. The gate cannot see the switch, so the rename procedure includes a smoke test of the start entry, and the phase report records the command that was run and the result.
The hygiene rule exists because of a real incident. An earlier phase left an application running, and a later rename failed with a sharing violation that looked like a permissions problem. The fix was to stop the process and retry, and the lesson is now encoded: no phase ends with a process it started still alive, and no rename is attempted without checking for one.

## 29. launch.ps1: errors, exit codes, and messages
Exit codes are stable: zero for success, one for any failure. Failures include an unknown input, a missing folder, a missing executable, a missing runtime, and a registry that cannot be parsed. The codes are not overloaded with meaning, because a shell operator reads the message, not the number, and a script that branches on seven codes is a script nobody maintains.
Messages are one line, ASCII, and self-contained. A failure names the input received, the folder it looked in, and the accepted values. It does not print a stack trace as its primary message, because a stack trace tells the reader where the script broke rather than what the operator did wrong. When a runtime is missing, the message names the runtime and the part that needed it.
Warnings are explicit and prefixed. A part that is present but not startable is not an error; it is a normal outcome, and the script reports it with its contents and folder rather than with a failure code. That distinction matters to the launcher's honesty: an empty seat is not a broken part, and conflating the two teaches the operator to ignore failures.
The script never suggests a destructive fix. It does not print a command that deletes a folder, resets a repository, or reinstalls dependencies. It points at the documentation section that describes the correct procedure, and the operator decides. That rule exists because a helpful-looking destructive suggestion is how a small problem becomes an afternoon of recovery.
Success messages name the part and the command that was started, so the output can be pasted into a report and read later without context. The message does not claim that the part is working, only that the process was started, because the launcher cannot know what happens after the process detaches. Any claim about behaviour belongs to the phase evidence, not to the launcher.
Error text is treated as documentation. It is reviewed during the launcher phase for accuracy, it is kept in ASCII so it survives any console encoding, and it is quoted verbatim in the phase report when a failure is being recorded. A vague error message is a defect with the same severity as a wrong result, because it costs the next operator the same time.

## 30. The manifest generator
One script writes every manifest: a per-part file in each part folder, and a launcher file in the launcher folder. It reads the registry, builds the records, and writes them with deterministic key order and a trailing newline. It is the only writer of these files, which is why a hand-edited manifest is treated as a defect rather than as a local customisation.
Each part manifest mirrors the registry record: codename, alias with a hash sign for null, title equal to the codename, folder, contents, and status. The launcher manifest additionally carries the product name, the window title, the folder, the role sentence, the entry file, the parts list in order, the ladder, the retired labels, and the resolve map. That is enough for a future packaged host to render identity without parsing HTML.
The script uses only built-in modules, creates directories recursively, and writes UTF-8 without a byte-order mark. It prints one line per written file and a warning when a folder cannot be written. It never deletes a folder it does not recognise, because a generator that cleans up aggressively is a generator that eventually deletes evidence.
A check mode is proposed. In check mode the script generates in memory and compares against disk, exiting non-zero on any difference without writing anything. That mode is what a continuous integration job would run, and it is also useful locally before a commit. Until it exists, the gate's manifest check is a partial substitute.
The generator runs after every registry edit, every codename change, and every folder move. Running it twice is harmless, which is the property that makes it safe to include in a procedure. The documentation phase verifies that no manifest is stale by running the generator and checking that git reports no changes.
The generator's output is not a source of truth. If a manifest and the registry disagree, the registry wins and the manifest is rewritten. That ordering is stated in the manifest readme and repeated here, because a reader who treats generated files as authoritative will eventually hand-edit one and lose the next regeneration.

## 31. The consistency gate: checks and meaning
The gate runs eight checks against the registry, the launcher HTML, and the launcher manifest. The first check compares the launcher title in the registry with the HTML title. The second compares the launcher manifest identity with the registry. The third compares the card count with the part count. The fourth compares the card codenames with the part codenames in order.
The fifth check compares the resolve keys with the ladder keys, including order. The sixth checks that every assigned alias appears on the ladder. The seventh checks that every part folder exists. The eighth checks that every alias value points at a codename that exists. Each check is named, and the names are stable so a report can say which check failed a year from now.
Each check prints PASS or FAIL with a detail string. The detail includes counts or names, for example eight versus eight, or the list of aliases in order. That detail is what makes a failure actionable: a reader does not have to open three files to discover that the ladder gained a word and the resolve map did not.
The gate fails on drift rather than on style. It does not check prose, does not check contents wording, and does not check whether a part is startable. Those are reviewed manually, and the report records the review. The gate is deliberately narrow so that it stays fast and so that a failure always means something structural, not a preference.
The gate is run after every registry edit, every launcher edit, and every folder rename. Its output is pasted into the phase report, because the claim that the gate passed is not evidence. When a phase cannot run the gate, for example because a tool is missing, the phase records that as a blocker rather than skipping the line.
New invariants become new checks. The planned additions are a skills parity check, a manifest byte-equality check, a vendor-naming scan, an ASCII scan, an origin completeness check, and an evidence-path existence check. None of them loosens an existing check, and each one is written only after the failure it would have caught has been seen at least once.

## 32. The consistency gate: output, future checks, and CI
Output is line-oriented and human-readable. Each line begins with PASS or FAIL, followed by the check name and a parenthesised detail. The last line summarises the passed count out of the total. The format is stable so that a report can quote it and a future parser can read it without a schema.
The output contains no colours, no timestamps, and no absolute paths, so it is byte-comparable across machines. That makes it usable as evidence: two runs on two checkouts produce the same text when the trees agree. It also means a diff of two outputs shows exactly which check changed state.
Future checks are listed here so they are not forgotten. A skills bundle parity check compares the provenance file against the skills directory. A manifest byte-equality check regenerates into memory and compares. A vendor-naming check scans authored prose for the product name outside allowed contexts. An ASCII scan fails any script containing non-ASCII characters.
Further checks cover provenance and documentation. An origin completeness check verifies the proposed registry field. An evidence-path check verifies that every declared path exists. A documentation link check verifies that paths named in markdown resolve. Each of these is a small script and a small addition to the gate, and each one closes a class of drift that is currently caught by manual review.
Continuous integration is optional for now but designed for. A job would run the generator in check mode, then the gate, and fail on either. It would not start any part, would not need the network, and would not require a Windows-only step until a part needs one. That is the whole CI story: two commands and a non-zero exit.
The gate's authority is procedural as much as technical. A green gate is necessary but not sufficient for a phase to pass, because a phase also needs its evidence block. A red gate is sufficient to stop work, no matter how small the change looks. That asymmetry is intentional: it is easier to justify waiting than to justify ignoring a failing invariant.

## 36. Part Aster: identity edits and the patch log
The identity edits are small and enumerated. The product configuration had its product name and application name fields renamed. The package manifest had its name and product name renamed. The local service binary was renamed to match the executable. One window-title literal was patched in the main bundle. Nothing else was modified in that phase.
The patch log records, for each change, the file, the offset, the old literal, the new literal, the hash before, and the hash after. That record is what makes the change reversible and auditable. A patch without a recorded offset is a rumour; a patch with one can be verified against a vendor update by checking whether the offset still contains the expected bytes.
Syntax verification follows every patch. The patched bundle is checked with the runtime's own parser before the application is launched, because a syntax error in a main bundle presents as a blank window rather than as a clear failure. Only after the check passes is the application started, and only after it starts are screenshots taken.
The relaunch is part of the evidence. The number of processes is recorded, both window titles are recorded, and the absence of a crash banner is recorded. Those three facts together are what justify the claim that the build works, and they are the reason a screenshot alone would be insufficient.
Reversal is documented with the same care. Restoring the literal, re-running the syntax check, and relaunching is the whole procedure. Because the identity edits are literal, reversal does not require the vendor's original binary, only the recorded old strings, which is why the log stores them explicitly.
The patch log never contains credentials, profile data, or endpoint secrets. It contains strings that are visible in the shipped resources, offsets into those resources, and hashes. That boundary is what allows the log to be committed without turning the repository into a leak.

## 37. Part Aster: limits and known risks
The first limit is structural: there is no C plus plus or Chromium source, so the native layer cannot be rebuilt. The modifiable surface is the JavaScript resource layer plus configuration. Any request that assumes deeper changes is answered with this limit rather than with an experiment that will fail later and more expensively.
The second limit is about updates. The build does not carry an update path that this project controls, and vendor updates would replace the patched resources. The plan does not attempt to build an updater; it records the version beside every offset so that an update can be recognised as invalidating the patch log.
The third limit is about profiles. The application stores data under a path derived from its name, and that path may be shared with an installed copy of the vendor application if the names collide. Renaming the executable affects the path, so renaming is a separate step with its own decision rather than a casual edit.
The fourth limit is environmental. Antivirus software and file indexers can quarantine or lock patched files, and a lock on the folder is exactly what blocks a rename. The mitigation is procedural: check for handles before a move, record a blocked move instead of forcing it, and never create a junction as a silent substitute.
The fifth limit is functional. Some surfaces may require sign-in, and some features may call vendor endpoints that this project does not control. Those are treated as external preconditions. The plan does not stub an account system, does not capture credentials, and does not claim that every feature works offline.
The sixth limit is evidentiary. The build proves that the extracted resources run; it does not prove that every feature behaves as the vendor intended. Claims in the report are limited to what was observed, and anything else is labelled as inference or left as an unknown. That discipline is what keeps the RE label meaningful.

## 38. Part Aster: the rebrand procedure
The rebrand targets visible strings only. Product-name literals in shipped JavaScript, stylesheets, and configuration are in scope. Endpoints, licence notices, update identifiers, crash-reporting identifiers, and account flows are out of scope. A patch that changes behaviour is rejected even if it makes the interface look more consistent.
The procedure starts with an inventory. The string extractor produces a list of candidates with file and offset, and each candidate is classified as product name, vendor URL, licence notice, or internal identifier. Classification is recorded, because the next reader needs to know why a string was left alone, not only why it was changed.
Then the mapping is decided. The product name becomes the part codename where the string is user-visible, and stays untouched where it is a technical identifier. Uniqueness is checked before a replacement: a literal that appears in twenty places is either replaced everywhere with a recorded count, or not replaced at all.
Every patch is followed by a syntax check and a relaunch. The syntax check catches a broken bundle before it becomes a blank window. The relaunch confirms that the changed surface renders and that nothing else regressed. Screenshots are taken before and after so the change is visible in the evidence rather than only in a diff.
The patch log records file, offset, old, new, and hashes, exactly as the identity edits do. Reversal restores the literal, and the log makes that mechanical. Any patch that cannot be reversed by restoring a literal is rejected, because the build must remain maintainable across vendor updates.
The gate for the rebrand is a clean launch plus a review of the visible surfaces. The review looks for vendor product names on the welcome surface, the menus, the window titles, and any about panel. If a vendor name remains because it is a legal notice or a technical identifier, that is recorded as an accepted exception rather than quietly left.

## 43. Part Zingma: source evidence and dependencies
Before any split, the dependencies are mapped. The window construction is located in the main bundle, the browser-window options are recorded, and the entry files, preload, and stylesheet are identified. The IPC channels the window uses are listed, and each host service it calls is classified as local or remote. That classification decides what a minimal host must provide.

The evidence file is text or JSON, with file paths and offsets for every dependency. Screenshots are supplementary. Each stub is logged with its reason, and each removed call is justified by an observation. The result is a document another engineer can replay, which is the only definition of evidence this project accepts.
The dependency map also informs the hosting decision. If the window needs only local services, a small host is enough. If it needs remote services, the seat is re-scoped or blocked. That decision is recorded in the brand document if it changes what the seat is, because a seat that becomes a shell around a remote surface is no longer the same product.
Unknowns are listed rather than smoothed over. If a service's purpose cannot be determined from the bundle, it is marked unknown and stubbed defensively. A later phase may remove the stub with new evidence, but the plan does not pretend that the unknown was resolved by careful reading alone.

## 44. Part Zingma: reverse-engineering steps
The steps are ordered to fail cheaply. First, extract the window bundle and its stylesheet into the part folder. Second, build a minimal host harness that loads the window with logging enabled. Third, render once and capture the console output. Fourth, list the missing services the log reveals. Fifth, stub them one at a time, re-rendering after each stub.
The reason for one stub at a time is attribution. If three services are stubbed at once and the window renders, nobody knows which stub mattered, and a later removal becomes guesswork. If a stub breaks the render, the last change is the cause. That is slower by a few minutes and faster by an afternoon.
The sixth step is removal. A call that the evidence proves unnecessary is removed rather than stubbed, because a stub that survives forever is technical debt disguised as caution. Each removal is recorded with the observation that justified it, so a future reader can disagree with the evidence rather than with a feeling.
The seventh step is rebranding. Visible strings are patched using the same literal-only rules as the host, followed by a syntax check and a relaunch. The eighth step is a launch command, and the ninth is a launcher entry, added only after the command is stable. Nothing is wired before it works.
Throughout, the work is log-first. Changes come after observations, never before. Every change is reversible, every failure becomes a named blocker, and no step opens a network connection. The output of the phase is a window that opens from one command, plus a list of what was stubbed and why.
The gate is the same set of claims stated at the start: one command, a rendered window, sixty seconds without a crash, enumerated stubs, no vendor branding, and an isolated profile. If any of them fails, the phase ends blocked with the failing claim named, which is more useful than a partial success that nobody can reproduce.

## 47. Part Sonar: discovery and classification
Discovery is a recorded search, not a hunch. The plan searches installed programs, package managers, container images, and local caches for a DeepSeek Harness artifact. Each hit is recorded with its path, size, and hash. A hit that cannot be hashed is recorded as unreadable rather than ignored.
Classification follows the rules stated in the provenance section. Archive-like artifacts get a member inventory. Electron-like artifacts get an asar or resources analysis. Managed artifacts get metadata inspection. Source packages get entry-point reading. Web surfaces force a re-scope decision rather than a desktop extraction.
Each class has a stop condition. No artifact found ends the phase blocked with the search commands and their output. An account requirement ends the step. A platform mismatch ends the step. A web-only surface ends the desktop plan and starts a re-scope decision. Those conditions are written down so that stopping is a planned outcome rather than a failure of nerve.
Once a class is chosen, the extraction rules apply. Hash the artifact, write a manifest, extract to a named directory inside the part folder, inventory entry points and configuration, and identify authentication requirements before running anything. The order matters because running an unidentified binary is the one action that can turn an analysis into an incident.
The first run is the smallest possible entry point, with logging enabled and the network monitored. The output is captured verbatim. If the tool is a command-line tool, the first-run evidence is terminal output; if it is a desktop application, it is a window and a log. Either is acceptable as long as it is replayable.
After the first run, the seat follows the same rebrand and evidence rules as the other RE parts. Visible strings are patched literally, syntax is checked, the first screen is reviewed for vendor naming, and the patch log is committed. The RE label appears in the readme before the first screenshot is taken.

## 48. Part Sonar: gates, risks, and follow-ups
The gates begin with classification and end with a repeatable run. Classification recorded, hash recorded, extraction directory named, entry point identified, first run reproducible, no crash within a minute, no unexpected network calls, no vendor branding on the first screen, stubs enumerated, evidence readme written, RE label present.
The risks are mostly about availability. The artifact may be private, web-only, backend-dependent, Linux-only, or account-gated. Each of those is a stop condition rather than a puzzle to solve in this phase. The mitigation is to record the blocker class and the exact error, and to avoid the temptation to substitute the official package.
A subtler risk is label drift. If the official package is installed for comparison, the seat's provenance becomes ambiguous, and a reader cannot tell which bytes ran. The plan forbids that comparison, and if it is ever needed it becomes a separate, explicitly labelled investigation rather than a step inside this seat.
Follow-ups are decisions about the shell. Whether Sonar is a window or a command-line surface, how it updates, whether it exposes skills, and whether the Plus alias stays are all open. The plan records them so the phase does not decide them by accident when it wires the launcher.
Evidence for this seat is the whole point of the phase. A search log with commands and output, a classification note with the reasoning, a first-run log, and a screenshot or terminal capture are what turn an unknown into a known. Without them the phase would end with an opinion.
The definition of done is a working reverse-engineered shell with a replayable run, or a named blocker. Both are acceptable. What is not acceptable is a seat that looks occupied but cannot be reproduced, because that is worse than an honest empty seat.

## 52. Skills inventory
The bundled skills live in the inbuilt tree, with four hundred forty-six files at three point three four megabytes. The set includes product skills such as the Repo Wiki generator and the MAD workflow, plus a vendored harness set of forty-seven entries and one materialised command workflow. The inventory is the authoritative list of what ships with the launcher rather than with a part.
Skills are copied rather than symlinked, so packaging stays simple and a missing link cannot silently break a skill. Duplicate names are checked by directory name, and a missing skill file means the directory is ignored rather than treated as a fatal error. Discovery is by directory, which is the convention the vendored set already follows.
The provenance document records, for each vendored directory, the source root, the file count, the main file, and a hash prefix. That document is the only authority on which files may be rebranded. A skill that is not listed is not rebranded, even if it mentions the vendor, because the listing is what distinguishes a vendored copy from product content.
No skill is loaded by the launcher, no skill runs automatically, and no skill is fetched at startup. Skills are a part-level concern, wired later and reversibly. That separation keeps the launcher dependency free and keeps a skill failure from taking down the surface that is supposed to start everything else.
Skills never contain secrets, never write outside their workspace, and never modify the registry. Those three rules are short because they are absolute. A skill that needs to write elsewhere is re-scoped, and a skill that needs credentials is rejected.
The inventory is a snapshot, not a permanent truth. When a vendoring pass happens, the count and the provenance document are regenerated, and the gate's future skills check compares them. Until that check exists, the documentation phase verifies the count manually and records it in the report.

## 53. Skills provenance and rebrand rules
Rebranding is narrow by design. Only product-name tokens in prose and path prefixes that point at the vendor's configuration directory are changed. Datasets, fixtures, and platform adapters are excluded, because changing them would make a skill's examples false or break the runtime that loads it.
The exclusion is not squeamishness about names. A dataset that describes a vendor's product must keep describing it, or every example built on it becomes misleading. A platform adapter's file name is part of a contract, and renaming it produces a skill that loads in one environment and fails in another.
The rebrand script is idempotent and logs every file and token count it changes. Running it twice changes nothing the second time, which is what allows it to be part of a repeatable vendoring pass. Manual edits to vendored skills are treated as drift, because the next pass would overwrite them without warning.
Provenance is what makes the narrow rule enforceable. Without the listing, a rebrand pass cannot distinguish a vendored file from a product file, and the safe choice becomes rebranding nothing. With the listing, the script can be aggressive inside its scope and conservative outside it.
Skills that touch reverse-engineered work carry the RE label. A skill that describes a patched build as supported software would contradict the provenance table and mislead the assistant that reads it. The label is part of the skill's content, not a comment beside it.
The gate for this section is a scan. No vendor product name outside provenance-listed files, no secrets, no vendor logos in assets, and a parseable provenance document. Anything else is a manual review recorded in the phase report.

## 54. Skills wiring
Skills are not wired into any part today. The plan wires them per part, behind a flag, so that a wiring mistake can be reversed without unpicking a build. The default root is the inbuilt bundle, and a part may override it when its own build ships skills.
The launcher never loads skills. A part declares its root when it starts, and a future host reads that declaration. This keeps the launcher dependency free and keeps skill failures from affecting the shell that starts everything. The launcher may print which root it would use, but it does not read the skills.
Wiring must not break vendor startup. That constraint is why the flag exists: a part whose bundled skills conflict with the vendored set can disable the vendored root without changing its build. Conflicts are reported by name and resolved by path order, and the order is documented when it is implemented.
Empty seats receive skills only after their builds exist. Wiring a seat that has no application would create a configuration that cannot be tested, and an untestable configuration is worse than an unwired one. The seat sections therefore treat skill exposure as a follow-up, not a phase task.
No skill is fetched at startup, no skill runs automatically, and no telemetry is emitted by default. Those defaults are recorded here so a future wiring change has to argue against them explicitly rather than adding a fetch because it is convenient.
The gate is small: the root exists, the provenance document parses, and no collisions are unreported. The rest is manual review, because skill behaviour is content rather than structure and a structural gate cannot prove that a skill does what it says.

## 55. The inbuilt bundle: folders and purposes
The inbuilt tree has five folders. The skills folder is populated. The extras folder holds three files at two point six four megabytes, and its contents are not yet identified. The agents, bundled, and plugins folders are empty and reserved. Each folder has a stated purpose so that an empty folder reads as a seat rather than as an accident.
The extras inventory is the first task of the bundle phase. Each file is recorded with its name, size, hash, and a one-line description of what it is for. Until that inventory exists, the folder is documented as unidentified rather than described optimistically. Nothing is deleted from it during this plan.
The reserved folders need an operator decision before they are filled. Agents would hold agent presets, bundled would hold assets shared by more than one part, and plugins would hold plugin bundles. Filling them without a decision would create content with no consumer, which is how a bundle becomes dead weight.
Every folder gets a readme and a manifest, including the empty ones. The readme states purpose and source, and the manifest lists files with hashes. An empty manifest is a valid record that says the folder is intentionally empty, which is more useful than a missing file that could mean either empty or forgotten.
The bundle is not a part folder and is not referenced by the registry. It ships with the launcher later, and it is not rebranded wholesale. That distinction matters because a rebrand pass over the whole inbuilt tree would hit datasets and adapters, which the provenance rules forbid.
Nothing is moved out of the bundle during this plan, and nothing is deleted. The bundle is treated as a shipping surface with its own rules, and those rules are written down before the content grows, not after.

## 56. The inbuilt bundle: manifests and gates
The bundle gates are simple and mechanical. Every subfolder has a readme. Every subfolder has a manifest. The manifests parse as JSON Lines. Hashes are full-length. No secrets appear in prose. No vendor product name appears in prose outside provenance. No vendor logos appear in assets. The skills count matches the provenance document.
The extras inventory is part of the gate because an unidentified file is an unknown in a shipping surface. The plan does not require knowing what every file does, but it requires recording that the file exists and that its purpose is unknown, which is a very different state from not noticing it.
The empty seats are documented as empty. A gate that required content would pressure the phase to invent content, and invented content is exactly what the provenance rules exist to prevent. An empty manifest with a readme is the correct record for a reserved folder.
Risks are about drift. Manifests go stale after edits, provenance lists go stale after a vendoring pass, and a rebrand can touch a dataset if the listing is wrong. Each of those is mitigated by regenerating rather than patching, and by reviewing the diff before committing.
Follow-ups are packaging decisions. Whether the bundle ships inside the launcher package, how it updates, whether it is signed, and what format plugins and agent presets take are all open. The plan records them so the bundle does not grow a format by accident.
The definition of done is a documented, manifested, rebrand-verified bundle. That is a modest goal, and it is deliberately modest, because the bundle is infrastructure for parts that do not exist yet and over-building it would be speculative work.

## 57. Reverse-engineering methodology: routing
Routing chooses the first move from the artifact type. An Electron or asar artifact goes to JavaScript analysis. An archive goes to member inventory. An MSIX or AppX goes to package identity. A managed assembly goes to metadata inspection. A native binary goes to layout and string evidence. A web surface goes to a re-scope decision.
The route determines the tool, and the tool determines what evidence is possible. JavaScript analysis can show code structure and string literals but cannot prove runtime behaviour. Member inventory can show what shipped but cannot show what runs. Package identity can show what is installed but not what it does. The plan states those limits instead of implying that one tool answers everything.
No decompilation claim is made without the tool that produced it. That rule sounds obvious until a summary loses the tool name and a reader assumes a decompiler was used. The evidence format therefore requires the tool and its version beside the finding, so a claim can be reproduced or challenged.
Extraction is conservative. Directories are named after the artifact, existing output is never overwritten, and re-extraction requires removing a marker rather than passing a force flag. Those rules are slower and prevent the one failure that destroys evidence: a second extraction that silently replaces the first.
Analysis never uses the network and never reads credentials. Outbound attempts by an artifact are recorded, not enabled. Account state is an external precondition, and a step that needs it stops rather than improvising a login. That boundary keeps the analysis reproducible and keeps the repository free of secrets.
Every finding is labelled as observation, inference, or unknown. The label is not decoration; it tells a reader how much weight the finding can carry. A plan built on inferences is a hypothesis, and a plan built on unknowns is a discovery task, and the two need different gates.

## 58. Reverse-engineering methodology: evidence format
Evidence is per part and lives in the part folder. Each evidence readme names the artifact, its hash, its version, the tools used, the date, and the extraction directories. It lists what was observed, what was inferred, and what remains unknown. It is written for replay, not for summary.
The manifest is JSON Lines with path, size, and hash for every file. It is generated rather than patched, and a mismatch with disk is evidence drift. Hashes are full sha256 strings, because a prefix is enough for a human but not enough for a verification script.
Patches are logged with file, offset, old literal, new literal, and pre- and post-patch hashes. The log is committed with the build and quoted in the report. A patch without an offset is a rumour, and a patch without a hash cannot be checked after a vendor update.
Screenshots are named by milestone and stored beside the readme. They never replace a technical claim; they prove a visual state. Logs are text with the producing command, truncated to the useful window when they are long, and always retained in full for the first run.
Vendor updates invalidate evidence. The version is stored beside every offset so that an update is recognised as a new baseline rather than as a mysterious regression. When a new artifact arrives, the old evidence stays for comparison and the new evidence is written separately rather than overwriting the old.
The evidence rules apply to every RE part: Aster, Zingma, and Sonar. Forks use a lighter form because their tree is the evidence, and packages use a hash-and-identity form because they are not modified. The provenance table records which form applies to each part.

## 59. Phase 0: baseline
Phase zero proves that the tree is consistent before any build work starts. It runs the gate, fixes any drift in the registry, regenerates the manifests, runs the gate again, and records the output. It also confirms that the eight part folders exist and that the skills count is what the inventory claims.
The phase records versions because version drift explains most mysterious failures. Node, PowerShell, the package manager, bun, and cargo are recorded if present, and an absent tool is recorded as absent rather than left blank. That record is what makes a later failure diagnosable instead of mysterious.
The alias tests are four commands: a codename, an alias, an unknown input, and a list. Each result is recorded. The list output is compared against the registry by eye, because the gate checks the HTML but not the script's table. That manual comparison is written into the evidence.
The phase also verifies the rename prerequisites. No process holds the Aster folder, no junction remains from the earlier rename, and no stale path points at the old folder. Those checks are cheap and they prevent the most likely failure of the immediate next phase.
The definition of done is a green gate, a launcher list that matches the registry, alias resolution working for the live aliases, and an unknown input failing with a clear message. If any of those fails, the phase is blocked and the failing command is quoted.
The evidence block is short by design: gate output, launcher output, versions, and a list of anything that was fixed. A baseline that takes a page to describe is a baseline that hid something, so the plan keeps it to the facts that would matter to a reader a month later.

## 60. Phase 1: launcher shell
Phase one finalises the shell. Card copy for the eight parts is confirmed, alias chips and status pills are checked, the footer is checked for the ladder and the registry path, and the title and product name are confirmed against the registry. No new logic is added to the shell in this phase.

## 61. Phase 2: parts wiring
Phase two makes every part resolvable and, where possible, startable. Ingot and Aster get smoke tests and their output is recorded. Chromix, Codeix, and GSX-CLI get inventories, and a start entry is added only where a run succeeds. The three seats remain non-startable and are reported honestly.

The deliverable is a per-part status table: startable, inventoried, or empty, with the evidence that justifies the status. A part that failed its smoke test is recorded as blocked with the exact error, not as present-but-probably-working.
The definition of done is two startable parts, six honest reports, and a green gate. That is a modest target, and it is deliberate: wiring a part that cannot build is not progress, it is a promise that will be broken later.

## 62. Phase 3: the three seats
Phase three fills the empty seats in risk order: Zenix first because the native application is the least risky, then Zingma because the split is a known artifact, then Sonar because its artifact is unknown. That order means the seat pattern is proven before the hardest case is attempted.

Each seat produces an evidence readme with its label, a launch command if it exists, and a list of stubs or blockers. Each seat's gate is stated in its section and repeated in the phase report. The phase does not average the seats into a single status; it reports a matrix.
The matrix is the deliverable: seat, label, status, evidence path, and blocker if any. A reader can see at a glance which seats are real, which are inventoried, and which are blocked, without reading three readmes. That is the same principle as the provenance table.
The definition of done is a seat matrix with no ambiguous entries. Each seat is either startable with evidence or blocked with a named reason. A seat that is almost working is recorded as blocked, because almost working is not a status this project recognises.

## 63. Phase 4: rebrand, bundle, and documentation
Phase four finishes naming and packaging. The string inventory runs over the Aster build, candidates are classified, product-name literals are patched, each patched bundle is syntax-checked, the application is relaunched, and the changed surfaces are captured. The patch log is updated with hashes.
The bundle work follows: the extras are inventoried, every folder gets a readme and a manifest, and the skill provenance is regenerated. A collision report lists duplicate skill names and records which one wins by path order. Nothing is deleted, and nothing is moved out of the bundle.
Documentation is updated in the same phase, because a rename that lands without documentation is half a rename. The brand document, the architecture readme, the launcher readme, and the report's current-state section are all checked against the registry. The definition of done is consistent naming, a documented bundle, updated documentation, and a green gate, with the stale-name search recorded. That is the last build phase, and it ends with the report rather than with a release, because the report is the artifact this project treats as proof.

## 64. Verification, risks, and open questions
Verification is a short list of commands and checks. The gate must print eight of eight and exit zero. The launcher list must match the registry. Alias resolution must work for the five live aliases. An unknown input must fail. The two startable parts must start and be stopped. Every phase must record versions and evidence, and no phase may leave a process running.
The risks are recorded with mitigations rather than with optimism. Handle locks can block the Aster folder move, and the mitigation is a process check before the attempt and a recorded blocker after a failure. Vendor updates can invalidate offsets, and the mitigation is recording the version beside every offset. Vendoring can reintroduce vendor naming, and the mitigation is the provenance list and the scan.
Two process risks matter as much as the technical ones. A restructure can break script paths, and the mitigation is deriving roots from script locations plus a documentation sweep. A rename can leave generated files stale, and the mitigation is the fixed order of registry edit, folder move, regeneration, and gate.
Open questions are listed so they are decided rather than discovered. Which host technology the packaged launcher uses. Whether Chromix and GSX-CLI ever receive aliases. Whether Zingma ships inside a host or as its own process. Whether a DeepSeek Harness artifact exists on this host at all. Whether copying Claude Desktop is acceptable under its licence. When, if ever, the Aster executable is renamed. What goes into the agents, bundled, and plugins folders.
The next action after approval is phase zero, and the first task inside it is the Aster rename checklist in section twenty-two, because every later section refers to the new name. The rename runs in one commit, ends with a green gate, and records the former name once in the report so that older checkouts remain navigable.
The stop condition for the whole plan is a green gate plus a written phase report, not a release. This project's definition of done has always been evidence plus consistency, and this plan keeps that definition rather than inventing a new one at the end. When the gate is green and the report is written, the plan is finished, and the next plan starts from the tree it leaves behind.
